## 教材疑義與處理

| 位置 | 容易造成誤解之處 | 命題處理 |
|---|---|---|
| 01 第 8 頁 | 標題年份與內文年份不同 | 不考該案年份與金額，聚焦工程活動與流程判斷 |
| 02 第 9、14 頁 | 功能有無與品質程度是教學上的簡化區分 | 用明確服務與品質限制辨析，不推論所有功能永遠只能二分評估 |
| 03 第 24、29 頁 | 故事點以工時比例舉例，可能被理解成固定時間單位 | 只問團隊內相對努力，不把點數強行換算為通用小時數 |
| 04 第 25、34～36 頁 | 流程教學部分用較傳統的帶領與分工說法 | 依同章明確列出的 PO 產品排序、Developers 開發計畫、SM 促進合作與自我管理出題 |
| 05 第 26 頁 | 欄位交接處使用 DoD 名稱，可能與 Scrum Increment 的 DoD 混淆 | 看板題聚焦 WIP、Blocked 與拉動，不以進入 Testing 當成產品已符合整體 DoD |
| 06 第 26 頁 | commit -a 的簡化敘述沒有明說未追蹤新檔例外 | 題目補足已追蹤與未追蹤條件，官方 Git 文件確認 -a 不加入新檔 |
| 06 第 58 頁 | pull 示範以 fetch + merge 說明，未涵蓋 rebase 設定 | 以 fetch 與整合區別命題，涉及 merge 的選項明示指定以 merge 整合 |
| 06 第 70 頁 | ignore 的介紹可能讓人以為對已追蹤檔也自動生效 | 補考既有追蹤及歷史不會自動消失，依官方文件核對 |
| 07 第 15 頁 | 耦合的首句以獨立程度表述，後續高低解釋才指出依賴方向 | 採清楚的高凝聚、低耦合與跨模組依賴語意 |
| 08 第 18～21 頁 | 第 19 頁同時顯示 Style 可共享與刪 Polygon→刪 Style，與聚合定義不一致；欄位程式本身也不足以證明所有權 | 依第 18 頁定義，於題幹明示共享、排他與刪除條件；不依類別名稱或 private 欄位猜組合 |
| 09 第 20～21 頁 | 條件覆蓋例子若套用短路求值，會影響條件是否實際執行 | 本題明示不考短路求值，以已記錄布林值判斷條件與整體決策 |
| 09 第 24、27、31 頁 | 範圍開閉、等第文字排序與邊界說法有些不夠精確 | 題幹明定整數、含端點及每個等第區間，明示要求內外鄰值，不沿用模糊敘述 |
| 10 第 5 頁 | 未來負載被描述為超載，兩者在一般實務不必然相等 | 不將未來負載一律當成超載；以是否超出承載能力區分 |
| 10 第 19 頁 | 將 10 秒 ramp-up 與 10 次 loop 直接解讀為 100 秒、1,000 requests | 明示每個 loop 的 Sampler 數計算總次數；不以 ramp-up×loop 推總耗時，依 JMeter 官方手冊核對 |
| 10 第 29～31 頁 | 平均值、P90 與「所有請求」條件的推論可能混用 | 分別測量平均、指定百分位與全部樣本條件，禁止用 P90 推出 100% 達標 |
| 11 第 18 頁 | 使用舊的 Master／Slave 術語 | 解釋為控制節點與執行節點，仍對應教材原詞 |
| 11 第 40 頁 | Runner 說成以 Docker 運作，會被理解為所有執行環境都必須容器化 | 只考其提供執行環境與執行 Job 的角色；官方文件確認也有 VM 等方式 |

## 出題與品質界線

每題只設定一個正確選項，錯誤選項對應具體誤解；計算題明確說明單位與條件，情境題盡量指出判斷前提。打散後重新檢查答案索引與選項診斷對應。

這是本次 AI 直接編寫及內容檢核的可部署候選題庫，沒有證據可宣稱已達到某個教師制定的量化品質門檻。未定義的上線門檻、難度與鑑別度仍需透過教師檢閱或學生試測評估。每目標只有一題，重複抽到同題的記憶效應也需要納入弱點解讀。
